## 4c. Bugs found and fixed

| Bug | Module | Role | Issue | Severity | Status |
|---|---|---|---|---|---|
| BUG-001 | Orders | Owner, Customer | A billed order keeps a "Paid" payment label typed before billing, even when its bill is unpaid. Payments later received on the bill never update the order. Live example: ORD000002 shows Paid; INV000007 has ₹282 due. | High | Fixed, retested |
| BUG-002 | Dashboard | Owner | The hero "Total Sales" shows ₹0 and the trend chart is empty: it groups sales by `sale_date` / `created_at`, but the API sends `invoice_date` / `createdAt`. | Medium | Fixed, retested |
| BUG-003 | Customer detail → Ledger History | Owner | Dates read `created_at` (Invalid Date). Balance reads `balance_after`; the API sends `running_balance`, so it shows ₹0. Payment links use `reference_id`, which is empty for ledger payments (PAY-null). | High | Fixed, retested |
| BUG-004 | Orders history, Sales mobile list, Customer view, Stock movements | Owner | Same `created_at` vs `createdAt` mismatch, so dates are blank, "—" or Invalid Date. | Low | Fixed, retested |

Only display or derived values were wrong. The stored ledger entries, bills and balances are correct, and no data was changed.

**Fixes (not committed):**
- **BUG-001:**
  - New `api/src/utils/orderPayment.ts`: a billed order's payment status is taken from its bill (Paid / Partial / Pending) in the owner order list and detail and in the customer portal list and detail.
  - On billing, an unpaid bill now sets the order to "Pending" instead of keeping the typed label.
- **BUG-002 to 004:** `Dashboard.tsx`, `CustomerDetail.tsx`, `Orders.tsx`, `Sales.tsx`, `CustomerViewModal.tsx` and `InventoryOverview.tsx` now read the field names the API actually sends.

**Retesting:**
- **BUG-001:** a new check in `npm run test:workflows` covers the order payment label at three points:
  - Set to "Paid", then billed unpaid → shows Pending.
  - ₹400 received → Partial.
  - ₹600 received → Paid, with the customer balance back to 0.

  It is checked in all four views. It **fails on the old code** (80 passed, 2 failed, every view showing "Paid") and **passes with the fix** (82 / 0).
- **Other suites:**
  - test:e2e 49/0
  - test:market-cart 42/0
  - test:marketplace 23/0
  - test:isolation 57 checks
  - test:roles 104/0
- **BUG-002 to 004:** checked in the browser against a mock API using the exact field names the live API returned. The ledger now shows dates, the running balance down to ₹282, and RCP receipt numbers. The dashboard hero equals the bill total and the chart draws. Order history shows times, and mobile sales show dates.

## 6. What is blocked, and why

- **Signing in.** I can't type passwords on the live site, so someone has to sign in in the browser pane for each role: super admin, shop owner, and a customer.
- **Writing test data to production.** Scenarios A to D create orders, bills, payments and ledger entries. Financial records are never edited or deleted (only reversed), so test entries would stay in the live books. This needs your OK, ideally in a dedicated test shop with a test customer.
- **Tenant isolation with real sessions.** This needs two shops (A and B) that each have an owner. As supporting evidence (not a substitute for live testing), I ran the automated suites today on a throwaway in-memory database:
  - `npm run test:isolation`: 57 cross-owner checks passed, no leaks.
  - `npm run test:roles`: 104 passed, 0 failed.
- **SHOW visibility on the live server.** This depends on Render having deployed commit 744ebee.
