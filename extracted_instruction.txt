Final Summary
1. Executive Summary and Business Context
NSYU is the parent company. It sells physical products and provides application/software services. PTL and MLT are separate owner workspaces within the business-management application. Each owner manages their own shops, staff, products, sales, customers, payments, reports and permissions. A user may be assigned to multiple shops; a separate login for every shop is not required.
The system must distinguish company-level administration, owner/workspace administration and shop-level operations. URLs such as /PTL or /mlt are navigation routes, not security boundaries. The API must authenticate the user and authorize every protected request.
1.1 Business goals
Manage product sales and application services in one business system.
Allow each owner to create and manage multiple shops.
Allow one user to be assigned to one or more shops, with independent permissions per shop.
Allow owners to control menus and actions: View, Create, Edit, Delete, Approve and Export.
Keep PTL and MLT data isolated unless a specific company-level role is authorized.
Keep stock, invoices, payments, ledgers, installments and payroll consistent and auditable.
Use PostgreSQL/Supabase through the backend as the authoritative business database.
Give React web and Flutter Android/iOS clients exactly the same business rules through one API.
1.2 Scope
In scope
Not specified in the brief (requires a decision before it is built)
All 17 confirmed sidebar modules (BUSINESS, PEOPLE, ADMIN)
Company, owner/workspace and shop hierarchy
User identities, shop assignments, roles and action permissions
Product sales, purchases, stock, billing, payments, ledgers and EMI
Employees, attendance and payroll
Application/software service sales and delivery
Reports, audit trail, security and release criteria
Online payment-gateway integration
GST e-invoicing / return-filing integration and accounting-software export
SMS / WhatsApp / email notification delivery (see D-23)
Offline-first mobile operation (see D-24)
Biometric or geo-fenced attendance devices (see D-18)
Separate sidebar modules for enquiries, quotations and projects (see D-19)
1.3 Assumptions and constraints
Currency is Indian Rupee (₹). Default time zone is Asia/Kolkata (IST).
The target stack is React + TypeScript + Vite (web), Flutter (Android/iOS), Node.js + Express + TypeScript (API), Sequelize (ORM) and PostgreSQL/Supabase PostgreSQL.
This document describes target requirements. It does not certify what the live website currently implements; compare with existing models, migrations and routes before changing anything.
Existing working APIs, models and UI patterns should be extended compatibly rather than rewritten.
1.4 How to read requirement wording
MUST marks a requirement that is confirmed in the owner's brief or is essential for security, financial integrity or tenant isolation.
SHOULD marks a recommended default that is sensible but still open to a business decision.
D-nn references point to the decision register in Appendix E. Where a decision is open, the document states the recommended default so development can proceed and be changed cheaply later.
Rule IDs such as PRD-01 or EMI-03 are stable identifiers for traceability between requirements, API checks and acceptance tests.

3.1 Identity versus assignment
A user account is the login identity; a shop assignment is a separate relationship. One email should normally map to one user identity, with multiple assignment records when needed. Each assignment can have its own role and permissions. Do not create duplicate user rows just because the user works in two shops.
If the same person is assigned to both PTL and MLT, allow this only if business policy explicitly permits it (D-02). Keep separate assignment and permission scopes and show the active workspace clearly. Otherwise reject cross-owner assignments.
3.2 User, employee and login are different things
A user can sign in. An employee is an HR record (Section 9.1). An employee may or may not have a user login, and a user (for example the owner or a company administrator) may have no employee record. When both exist they are linked one-to-one. Creating an employee MUST NOT create a login automatically; access is granted separately in Roles & Permissions.
3.3 Separation of duties
The person who prepares a payroll run SHOULD NOT be the person who approves it.
The person who requests a stock adjustment above the configured threshold SHOULD NOT be the person who approves it.
Discount overrides, invoice cancellation, EMI waivers and ledger adjustments require a separate Approve permission.
A user MUST NOT be able to grant themselves permissions they do not already hold.
3.4 Role templates and custom roles
The system ships role templates (Owner, Shop Admin, Manager, Cashier, Inventory User, Read-only). Templates are seed data and read-only. Owners may create custom roles inside their own workspace by combining module/action permissions; custom roles are workspace-scoped and cannot exceed the owner's own authority. A role that is still assigned to a user cannot be deleted.
4. Login, Authentication and Workspace Selection
User opens the company, PTL or MLT route and submits email/password over HTTPS.
Backend validates credentials and account status, then establishes the configured secure session/token.
Frontend requests the current profile, allowed workspaces, shop assignments and effective permissions.
If the user is not authorized for the requested workspace, show access denied or an authorized workspace selector.
User selects an authorized shop; owners may have an All Shops view for consolidated reports.
Every protected API request rechecks identity, scope and action permission on the server.
4.1 Route is not authorization
Changing /PTL to /mlt must not grant access. The API must not trust workspaceId or shopId sent by the browser without checking the authenticated user's assignment. Hiding a menu is a usability feature, not a security control.
4.2 Session rules
Logout invalidates the session according to the chosen auth strategy.
Expired/revoked sessions return an authentication error and the client returns to login.
Permission changes must take effect promptly; sensitive APIs must not trust stale frontend state.
Never store plaintext passwords in browser storage, mobile storage or logs. Mobile apps store tokens only in the platform secure store (Keychain / Keystore).
Use safe login failure messages that do not disclose whether an email exists.
Idle timeout and maximum session age are configurable in Settings > Security; Owner and Company roles SHOULD have shorter limits.
4.3 Account lifecycle
Event
Required behaviour
Create / invite
Owner (within own workspace) or company admin creates the identity. New users have no shop access until assigned. Invitation or temporary credential expires and forces a password change at first sign-in.
Password reset
Time-limited, single-use reset link or owner-initiated reset. Reset invalidates existing sessions. The response never reveals whether the email exists.
Lockout / throttling
Repeated failures are rate-limited per account and per IP. Lockout is temporary and audited.
Deactivate
Blocks login and revokes sessions immediately. Historical records and audit entries keep the user reference. Deactivation is preferred over deletion.
Reactivate
Allowed by an authorized owner/admin; prior assignments are restored only if the owner confirms them.
Delete
Allowed only for identities with no business or audit references; otherwise deactivate.
4.4 Credential policy
Passwords are stored only as strong salted hashes (for example Argon2id or bcrypt with an adequate cost factor).
The system SHOULD enforce a minimum length and reject common or previously breached passwords.
Multi-factor authentication SHOULD be available, and recommended for Owner and Company roles (D-22).
Any real password that has been shared in chat, e-mail or documents MUST be changed. This document intentionally contains no passwords.
4.5 Active workspace and shop context
The selected workspace and shop are shown permanently in the application header.
The client may remember the last-used shop for convenience, but the server validates the shop on every request using the path or payload identifier against the user's assignments.
Switching shop clears shop-scoped client caches (lists, drafts, cart) so data from one shop is never shown under another.
A user with exactly one assigned shop is placed in that shop automatically and sees no shop switcher.
5. Multi-Shop Assignments and Permission Model
5.1 Assignment rules
A shop belongs to one owner/workspace. A user may be assigned to one or multiple shops; multiple users may be assigned to the same shop. Assignment records include the granting owner, status, role and creation/update timestamps.

5.3 Permission codes and dependencies
Permissions are atomic codes written module:action, for example sales:create or payroll:approve. The full catalogue is in Appendix C. The server enforces these dependencies, and the permission editor mirrors them:
Create, Edit, Delete, Approve and Export each require View on the same module.
Approve never implies Create or Edit; separation of duties depends on this.
view_cost, view_sensitive and similar field-level permissions are separate from View.
5.4 How a request is authorized
Authenticate the token/session and load the user (must be active).
Resolve the target shop (and therefore its workspace) from the record or path, not from a client-supplied workspace value.
Find an active assignment of the user to that shop (or an owner/company grant that covers it).
Resolve the role's module/action permissions plus any per-assignment overrides.
Require the requested module:action to be allowed; otherwise return a safe authorization error.
Apply field-level filtering on the response and re-check ownership on every referenced child record.
5.5 Owner grants access
Owner opens Roles & Permissions.
Owner invites/creates a user or selects an existing identity.
Owner assigns one or more shops within their own scope.
Owner selects a role template or configures module/action permissions.
Backend validates that the grantor may grant those permissions.
System saves assignment changes and writes an audit event with before/after values.
Subsequent requests enforce the updated access; revoked shop access is denied.
5.6 Safe defaults
New users have no shop access until explicitly assigned.
New assignments use least privilege, not full access by default.
Delete/cancel, payroll, user administration, settings, exports and financial adjustments are restricted by default.
Owners cannot grant permissions beyond their own authority.
Removing one shop assignment must not remove other valid assignments, but must immediately block the removed shop.
5.7 Propagation and revocation
Permission and assignment changes MUST take effect on the next request. Either evaluate permissions from the database on each request, or keep a per-user permission-version counter that is bumped on every change and checked against the token. Long-lived tokens that embed permissions are not acceptable for sensitive actions.

7. Detailed User Journeys
7.1 Owner views all shops
Owner signs in with their owner account.
Backend returns shops linked to that owner's workspace only.
Dashboard offers All Shops and individual shop filters.
All Shops aggregates only the current owner's shops; PTL and MLT figures are never accidentally combined.
Selecting a shop scopes lists, forms, reports and write operations to that shop.
7.2 Owner creates a shop
Owner opens Shops > Add Shop and enters name, code, contact details and required settings.
Backend checks the shops:create permission and validates required/unique fields.
Backend creates the shop linked to the authenticated owner's workspace.
System initializes settings from workspace defaults without copying private data from another shop.
Owner assigns users and roles.
The new shop appears only for authorized users.
7.3 One user has multiple shops
Example: a PTL manager is assigned PTLS and RTLS. They can switch between both. Billing Create may be enabled for PTLS but View-only for RTLS. The API must reject creating a bill in RTLS even if the user manipulates the frontend request.
7.4 Cross-owner access
A user can be assigned to PTL and MLT only if the business explicitly supports it (D-02). Each workspace owner controls their own assignments. The active workspace must be visible, and all data/actions must be scoped independently.
7.5 Onboarding a new staff member
Owner or authorized Shop Admin creates the employee record (Employees).
If the person needs to sign in, the owner creates or invites a user identity and links it to the employee.
Owner assigns shop(s) and a role template, then adjusts permissions per shop.
The person signs in, sets a new password and sees only the assigned shops and menus.
Audit shows who created the user, who granted which permissions and when.
7.6 Offboarding or reassigning a staff member
Owner marks the employee as resigned/terminated with an effective date (history is kept).
Owner deactivates the user or removes the shop assignments; sessions are revoked and access is blocked on the next request.
Open items (draft invoices, pending approvals) are reassigned or closed.
For a shop transfer, add the new assignment first, then remove the old one; the employee's shop history records both with effective dates.
7.7 Deactivating or closing a shop
Owner chooses Deactivate on the shop; new sales, purchases and stock movements are blocked.
Remaining stock is transferred to another shop of the same workspace, sold, or written off through an approved adjustment.
Outstanding receivables, payables and active EMI plans stay visible and collectable (or are explicitly transferred).
Historical records, reports and audit entries remain; the shop is never hard-deleted once it has transactions.
8. Business Modules
Each module below states its purpose, key data, lifecycle, enforceable rules and permissions. Money amounts are in ₹. Server-side validation is authoritative in every case.
8.1 Products
Purpose. Maintain the catalogue of physical products and (per 11) service items that can be purchased, stocked and sold.
Key data. Stable ID, SKU/code, name, description, category, unit, product type (Physical or Service), purchase price, fixed margin amount, derived selling price, tax configuration (rate, inclusive/exclusive, tax classification code if used), reorder level, barcode (optional), status (Active, Inactive, Archived).
ID
Rule / requirement
PRD-01
Selling Price = Purchase Price + fixed Margin Amount (₹), not a percentage. Example: purchase ₹500 + margin ₹100 gives a base selling price of ₹600 before configured tax/discount. The system never silently reinterprets the margin as a percentage.
PRD-02
The selling price is calculated by the server whenever purchase price or margin changes and is shown read-only in the form. Overriding the price at billing is not permitted unless a separate permission is granted (D-06).
PRD-03
Changing purchase price or margin affects future sales only. Historical invoices and purchase lines keep their own snapshots.
PRD-04
SKU/code is unique within the catalogue scope (D-03) and compared case-insensitively after trimming.
PRD-05
Products referenced by any transaction cannot be deleted; they are archived. Archived products cannot be added to new documents but remain in history and reports.
PRD-06
Service-type products never hold stock and never create stock movements.
PRD-07
Purchase price, margin and stock valuation are sensitive fields shown only with products:view_cost (and inventory:view_cost for valuation).
PRD-08
Validation: name, unit and SKU required; purchase price ≥ 0; margin ≥ 0 (a negative margin is rejected unless D-06 allows it); amounts have at most two decimals.
PRD-09
Bulk import/export uses a validation preview before commit; export needs products:export and is audited.
PRD-10
Whether a new purchase at a different cost updates the product's purchase price (last cost, weighted average or manual only) is a business decision (D-12). Until decided, purchase price changes only by explicit edit.
8.2 Inventory
Purpose. Track stock per shop and keep a complete, immutable history of every change.
Stock movement types. Opening balance, Purchase receipt, Sale, Sale return, Purchase return, Adjustment increase, Adjustment decrease, Transfer out, Transfer in, Cancellation reversal.
ID
Rule / requirement
INV-01
Stock is held per (shop, product). Receiving stock into PTLS never changes RTLS.
INV-02
Every change to quantity writes a movement record containing shop, product, signed quantity, movement type, source document, actor, timestamp and reason where applicable. Movement records are never edited or deleted.
INV-03
Quantity on hand cannot become negative unless the shop setting "allow negative stock" is enabled (default off, D-13). A sale that would cause negative stock is rejected and nothing is written.
INV-04
Manual adjustments require a reason code and inventory:edit. Adjustments above a configured quantity/value threshold need inventory:approve from a different user (D-10).
INV-05
Transfers are allowed only between shops of the same workspace (D-21) and follow Dispatched → Received. Stock is "in transit" between the two steps. Both shops' permissions apply (create at source, receive at destination). Cross-workspace movement is treated as a normal sale and purchase, not a transfer.
INV-06
A stock count (stocktake) session records counted quantity against system quantity and produces approved adjustment movements for the differences.
INV-07
Stock updates use row-level locking or atomic conditional updates so concurrent sales cannot oversell the same units.
INV-08
Low-stock indicator appears when quantity on hand ≤ product reorder level (or the shop default).
INV-09
Reconciliation: the stored balance MUST equal the sum of that product's movements for the shop; a scheduled check reports any mismatch.
8.3 Purchase
Purpose. Record purchases from suppliers, receive stock and create supplier payables.
Lifecycle. Draft → (Ordered, optional) → Partially Received / Received (posted) → Cancelled. Payment status (Unpaid, Partly paid, Paid) is derived from Payments and does not change the document status. A Purchase Return is a separate document linked to the original.
ID
Rule / requirement
PUR-01
A purchase captures shop, supplier, supplier invoice number/date, line items (product, quantity, unit cost, discount, tax), other charges and totals. Line values are saved as snapshots.
PUR-02
Stock increases only when quantity is received/posted, never merely because the document was saved. Partial receipts are supported; total received cannot exceed ordered quantity unless over-receipt is explicitly allowed.
PUR-03
Posting creates the supplier payable and the stock movements in one database transaction; any failure leaves no partial stock or ledger entry.
PUR-04
The supplier invoice number is unique per supplier; a duplicate is rejected or requires explicit confirmation.
PUR-05
A posted purchase cannot be edited. Corrections use cancellation (only if no dependent movement makes it impossible) or a purchase return/adjustment, always with a reason and audit entry.
PUR-06
A purchase return reduces stock and the supplier payable (or creates supplier credit). Returned quantity cannot exceed received minus already returned, and the stock must be available.
PUR-07
Purchase cost fields are sensitive and visible only to roles with cost permissions.
PUR-08
Each purchase has a unique document number generated by the server (12.3).

The Sales menu is the record of the sale and its status; the Billing menu creates and prints the invoice (8.5). For a counter sale one action creates the sale and its invoice in a single transaction. ID
Rule / requirement

SAL-02
The server validates product status, shop stock, price, tax and discount limits. Totals sent by the client are never trusted.
SAL-03
A sale for a named customer is required for credit sales and EMI; whether anonymous walk-in sales are allowed for fully paid bills is configurable (D-14).
SAL-04

SAL-05

SAL-06

SAL-07

BIL-02

BIL-03

BIL-04

12. Cross-Cutting Business Rules
12.1 Money and quantities
Store money as exact decimals (for example numeric(14,2)) or integer paise; never binary floating point.
Currency is ₹ with two decimals. Rounding happens at one defined step and with one defined mode (D-05); the same rule is used by API, web and Flutter.
Quantities allow the decimal places needed by the unit (whole numbers for pieces, up to three decimals for weight/length).
Shared test vectors (input → expected totals) are maintained and run against API, React and Flutter calculation code.
12.2 Dates, time and financial year
Timestamps are stored in UTC; screens and reports display Asia/Kolkata (or the shop time zone).
Documents also carry a business date (for example invoice date) separate from the creation timestamp.
Financial year default is 1 April – 31 March (D-20) and drives numbering sequences and period reports.

12.5 Idempotency
Create operations for invoices, purchases, payments and EMI collections accept an idempotency key (client-generated unique value). The server stores the key with the result for a retention window; a repeat with the same key and same payload returns the original response, and a repeat with the same key but different payload is rejected.
12.6 Concurrency
Editable records carry a version number; an update with an outdated version is rejected with a conflict error and the user is asked to reload.
Stock and sequence updates use row locks or atomic conditional statements inside the transaction.
Operations that touch stock, invoice, payment and ledger run in one transaction and roll back completely on any failure.

13.2 Data ownership rules
Every shop-owned record must have a valid shop relationship.
Every shop must resolve to one workspace/owner.
Do not trust workspaceId/shopId from the browser without server-side assignment validation.
Decide explicitly whether product/service catalogues are company-shared or workspace-specific (D-03); stock stays shop-specific.
Use database constraints and transactions to preserve integrity.
Scope queries in service/repository paths, not only in UI filters or controller checks.
13.3 Constraints and indexes (recommended)
Area
Constraint / index
Identity
Unique normalized email; unique (user_id, shop_id) assignment; foreign keys with restricted delete.
Shops
Unique (workspace_id, code) (or global, per D-09); status check.
Stock
Unique (shop_id, product_id); check quantity ≥ 0 unless negative stock allowed; movements append-only.
Documents
Unique (shop_id, fiscal_year, number) for invoices/purchases/payments; status transitions validated; amounts ≥ 0 checks.
Cross-tenant integrity
Child tables carry shop_id (and workspace_id where useful) and composite foreign keys so a line cannot point to a product, customer or invoice from another workspace.
Payments
Sum of allocations per payment ≤ payment amount; allocation ≤ document outstanding (enforced in transaction, verified by reconciliation).
Idempotency
Unique (scope, key).
Performance
Indexes on (shop_id, date), (shop_id, status), (customer_id), (due_date) for EMI, and search columns used by lists.
13.4 Owner isolation
PTL requests must be scoped to PTL and the authenticated user's PTL permissions. MLT users must not access PTL records by guessing IDs. PostgreSQL row-level security (RLS) may provide defense-in-depth where appropriate, but it does not replace backend authorization. If Supabase client libraries could reach tables directly, RLS MUST be enabled on every business table; the preferred design is that clients only call the backend API.
13.5 Catalogue decision
Business decision (D-03): are products/services maintained centrally by NSYU and shared with PTL/MLT, or does each workspace own its catalogue? A common option is a company master catalogue with workspace/shop activation and local pricing/stock. Select and document one model before migration.
13.6 Migration and backfill
Inventory existing tables, columns and routes; produce a mapping to this model and note gaps.
Back up the database and verify the restore before any structural change.
Add workspace/shop relationships and backfill every existing record; any record that cannot be assigned unambiguously goes to a review list, not a guess.
Run reviewed, versioned migrations (no automatic schema sync in production).
Run reconciliation (stock = movements; ledger = invoices − receipts) before and after migration and keep the evidence.

Authenticate the request.
Resolve the user's identity and the target workspace/shop context from the record or path.

Validate payload and business rules.

Record an audit event for sensitive/financial actions.
Return only authorized fields with a consistent error format.

All errors use one JSON shape so web and mobile can handle them in one place:
{ "error": { "code": "INSUFFICIENT_STOCK", "message": "Only 1 unit available", "status": 409,  "fields": { "items[0].quantity": "exceeds stock" }, "requestId": "..." } }
14.5 Client rules
React and Flutter use the same API contract and the same business calculations.
No fake production data, hardcoded business credentials or mock fallback responses in production.
The frontend hides unauthorized controls for usability; the API is authoritative.
Show the active shop/workspace clearly; validate the selected shop server-side.
Use idempotency keys (or equivalent duplicate-submission protection) for bills/payments, and disable submit buttons while a request is in flight.
Never place database passwords, service-role keys or private service-account keys in web or mobile bundles; clients talk only to the backend API.

Tokens in Keychain/Keystore; screens containing sensitive data respect OS privacy settings where practical.

A minimum supported app version can be enforced from the server.
15. Security, Audit and Reliability
15.1 Credentials and secrets
Store password hashes, never plaintext passwords.
Use HTTPS for deployed clients and APIs.
Keep secrets in environment/secret management, not source control or frontend bundles.
Remove hardcoded database credential fallbacks; fail fast if production configuration is missing.
Never package database passwords, service-role keys or private service-account keys in web/mobile clients.
Rotate any key or credential that has been exposed (including any password shared in chat or documents) and review access history.
15.2 Application security controls
Area
Requirement
Input handling
Validate and sanitise all input server-side; use parameterised queries via the ORM; never build SQL from user text.
Output / XSS
Escape user-supplied content in web and PDF output; use a restrictive Content-Security-Policy.
CSRF / tokens
If cookies are used for sessions, apply SameSite and CSRF protection; if bearer tokens are used, keep them out of long-lived browser storage where possible.
Rate limiting
Throttle login, password reset and write-heavy endpoints; return 429.
Authorization tests
Automated tests for every protected endpoint prove cross-workspace, unassigned-shop and missing-permission calls are denied.
Files
Validate type/size, store privately, serve through authorized short-lived links.
Dependencies
Automated dependency and secret scanning in CI; patch critical issues promptly.
Privacy
Collect only needed personal data; restrict customer, employee and payroll data by permission; log exports.
15.3 Deployment and database
Use an explicit CORS origin allowlist, especially when credentials are enabled.
The public health endpoint reveals minimal status; detailed DB errors belong in protected logs.
Use reviewed migrations for production schema changes; avoid unsafe automatic schema sync in production.
Separate dev/test/prod configuration and verify the active database/profile at startup so production never runs on an unintended development or in-memory database.
Back up data and test restoration before releases affecting financial records.
15.4 Sheets/Drive retirement
If PostgreSQL/Supabase is authoritative, Google Sheets/Drive must not remain a competing write path for products, sales, invoices, payments or ledgers. Inventory existing integrations and replace business writes with API calls. Retain file storage only for a separately approved use case; never expose a private service-account key in an app.
15.5 Audit trail
Record actor, timestamp, workspace, shop, action, entity, outcome and (for changes) before/after values.
Audit permission changes, user/shop assignments, price changes, invoice cancellation, stock adjustments, payment edits/reversals, ledger adjustments, EMI waivers/reschedules, payroll approval/unlock, settings changes, exports and logins/lockouts.
Do not log passwords, access tokens or private keys.
Audit logs are append-only, visible only to authorized roles, and retained per D-11.
Use reversals/adjustments for posted financial records instead of silent edits or hard deletes.
15.6 Reliability, backup and recovery
Automated backups with point-in-time recovery if the platform supports it; restoration is tested on a schedule, not only assumed.
Recovery point and recovery time objectives (RPO/RTO) are defined with the business (D-11).
Monitoring and alerts for API errors, slow queries, failed jobs (for example overdue-status or reminder jobs) and reconciliation differences.
Structured logs with request IDs, kept free of secrets and personal data where possible.
A documented rollback plan accompanies every release that changes financial data structures.

16.2 Metric definitions
Combined totals must avoid double-counting payments, shared records and carried-forward balances. Label these measures distinctly everywhere:
Measure
Definition
Invoice total (billed)
Sum of grand totals of issued, non-cancelled invoices in the period, net of credit notes.
Collections
Sum of customer payments received in the period (by payment date), regardless of invoice date.
Outstanding (receivable)
Sum over invoices of total − allocated payments − credits, at the report date.
Revenue
Billed value excluding tax, net of returns/credit notes (recognition rules per business).
Gross margin
Selling value − purchase-cost snapshot of items sold (requires cost permission).
Stock value
Quantity on hand × valuation cost under the chosen costing method (D-12).
Overdue EMI
Installment balance where due date + grace days < report date.
Reports use a consistent time zone (IST by default), the ₹ currency and one rounding rule.

19.3 Release blockers
PTL can read/write MLT data, or vice versa, without approved cross-workspace access.
A restricted action can be executed through a direct API call.
A sale, payment or EMI collection can leave stock, invoice or ledger inconsistent.
A production secret is committed or bundled into a client.
The live app uses an unintended development/in-memory database.
A financial release has no verified backup and rollback plan.
19.4 Definition of done (per module)
Rules in this document for the module are implemented server-side and covered by automated tests.
Authorization tests exist for every endpoint (allowed, wrong shop, wrong workspace, missing permission).
Web and Flutter screens show loading, empty, error, forbidden and success states.
Audit events are written for the sensitive actions listed in 15.5.
Reports for the module reconcile with transactional data.
19.5 Rollout and cutover
Deploy to a test environment with seed data using the real labels (PTL, MLT, PTLS, RTLS, MLTS, MTLS).
Run the full acceptance suite and reconciliation reports; fix defects.
Pilot with one workspace and shop, comparing results with existing records for an agreed period.
Back up, migrate remaining data, run smoke tests and reconciliation.
Release to the second workspace; keep the rollback plan available until the first period close is verified.

Appendix B. Example Scenarios
Scenario 1 — PTL consolidated sales
The PTL owner signs in and selects All Shops to see PTLS + RTLS totals. Selecting PTLS filters to PTLS. MLT shops never appear in the PTL selector.
Scenario 2 — Manager assigned to two PTL shops
The PTL owner assigns a manager to PTLS and RTLS. The manager can switch shops. If Billing Create is enabled only in PTLS, the API rejects bill creation in RTLS.
Scenario 3 — MLT owner adds a shop
The MLT owner creates a new MLT shop, assigns users and permissions, and the new shop remains invisible to PTL by default.
Scenario 4 — Company reporting
If NSYU needs reports across PTL and MLT, define a company-level permission and specify which fields are visible. Do not automatically grant cross-owner visibility to nsyu.mnt@gmail.com.
Scenario 5 — Same user across owners
If permitted, one identity can have separate PTL and MLT assignments. Show the active workspace and enforce separate permissions. Otherwise reject cross-owner assignment.
Scenario 6 — Credit sale on EMI
A cashier at PTLS bills ₹12,000, records a ₹3,000 down payment and, with approval where required, converts the balance into three monthly installments. The ledger shows one invoice debit and one down-payment credit; each installment collection is a payment allocated to the same invoice. If the second installment is missed, the plan shows Overdue and the manager sees it in the overdue list.
Scenario 7 — Month-end payroll
The attendance for the month is completed and corrected where needed. The payroll preparer calculates the run; the owner reviews and approves it, which locks the attendance dates. Salaries are paid, payslips are generated, and a later correction is posted as an adjustment in the next period.
Scenario 8 — Mixed product and service bill
A bill contains a physical device and a software setup service. On posting, only the device line reduces PTLS stock; both lines keep their own price and tax snapshots and appear in sales and service-revenue reports as appropriate.

Appendix D. Glossary
Term
Meaning
NSYU
The parent company: product sales and application/software services.
Workspace
An owner's tenant inside the application (PTL or MLT).
Shop
A selling location inside a workspace (PTLS, RTLS, MLTS, MTLS …).
Assignment
The link giving a user access to a shop with a role and permissions.
Fixed margin amount
A rupee amount added to purchase price to derive selling price; not a percentage.
Snapshot
Values copied onto a document when it is issued so later edits do not change it.
Idempotency key
A unique value that makes a repeated request return the original result.
Posted / Issued
A document that has taken effect on stock and ledgers and can no longer be edited.
Reversal / credit note
A new entry that cancels the effect of a posted entry, leaving history intact.
Outstanding
Invoice total − payments allocated − credits.
EMI
Equated monthly installment: a schedule for collecting a credit sale.
RLS
PostgreSQL row-level security, a defense-in-depth layer.
RPO / RTO
Maximum acceptable data loss / maximum acceptable downtime after a failure.

Final Summary
The intended design is an NSYU company platform with separate PTL and MLT owner workspaces, multiple shops per owner, unique login identities, multi-shop assignments and owner-controlled menu/action permissions. The 17-item sidebar (BUSINESS, PEOPLE, ADMIN) is the confirmed navigation for both workspaces.
Server-side authorization must scope all business data by workspace and shop. Product sales, stock, purchases, payments, ledgers, EMI installments, attendance and payroll use the same API and the authoritative PostgreSQL/Supabase database, with transactions, idempotency, audit trails and explicit acceptance tests. Selling price follows the fixed-margin rule: purchase price + margin amount.
Reconcile this requirements document with the existing code before implementation, settle the open decisions in Appendix E, and treat any password shared in chat as compromised until it has been changed.
